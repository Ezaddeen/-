# دليل تطوير بصمة أنامل

هذا الملف هو المرجع الهندسي قبل إنشاء أي ملف أو تعديل ميزة أو حذف كود. يعرّف أسلوب بناء منصة بصمة أنامل باستخدام Laravel وBlade وFilament، ويهدف إلى إبقاء النظام مفهومًا وآمنًا وقابلًا للتوسع دون تعقيد أو تكرار.

الوثيقة تصف المعمارية المستهدفة؛ لا يعني وجودها أن هيكل Laravel أو الحزم المذكورة قد أُنشئت بالفعل. يجب اعتماد إصدارات Laravel وPHP والحزم المتوافقة عند تهيئة المشروع.

## 1. قرارات التقنية

- **Laravel:** التطبيق والباك اند، المسارات، المصادقة، التحقق من المدخلات، الصلاحيات، قاعدة البيانات، الإشعارات والمهام.
- **Blade:** واجهة المتجر العامة وصفحات العميل والبائع. تبقى الواجهة ضمن تطبيق Laravel، ولا ننشئ SPA منفصلة في النسخة الأولى.
- **Filament:** لوحة الإدارة الداخلية لإدارة المستخدمين والبائعين والتصنيفات والمنتجات والطلبات والإعدادات. لا نستخدم Filament بدل واجهة المتجر أو لوحة البائع المخصصة.
- **CSS:** Tailwind CSS إذا كان متوافقًا مع starter kit المعتمد؛ تستخدم مكونات Blade مشتركة للتصميم المتكرر.
- **JavaScript:** يقتصر على التفاعلات الصغيرة التي لا يحلها Blade؛ لا نضيف إطار JavaScript آخر دون حاجة موثقة.
- **قاعدة البيانات:** MySQL أو MariaDB في بيئة التشغيل، مع بيئة محلية مماثلة قدر الإمكان.
- **الاختبارات والتنسيق:** PHPUnit أو Pest بحسب إعداد المشروع، وLaravel Pint لتنسيق PHP.
- **المصادقة:** starter kit رسمي ومتوافق مع إصدار Laravel المختار. لا نبني تسجيل الدخول أو تشفير كلمات المرور من الصفر.

لا تثبّت حزمة قبل مراجعة توافقها وصيانتها وإصدار Laravel المستهدف، وشرح الحاجة التي لا تغطيها أدوات Laravel الحالية.

## 2. مبادئ التصميم الهندسي

### Clean Code وSOLID

- اختر أسماء واضحة للصفوف والطرق والمتغيرات، واجعل كل طريقة تؤدي عملًا مفهومًا واحدًا.
- اجعل لكل صف مسؤولية أساسية محددة، وافصل العرض والتحقق والصلاحيات عن قواعد العمل.
- فضّل التركيب (composition) على سلاسل الوراثة غير الضرورية.
- اعتمد على واجهات أو عقود عندما توجد حاجة فعلية لتبديل تنفيذ أو اختبار حد خارجي، لا لمجرد إضافة طبقات شكلية.
- اجعل قواعد العمل قابلة للاختبار، ولا تضع منطقًا معقدًا داخل Blade أو Filament Resource.

### DRY وKISS وYAGNI

- **DRY:** لا تكرر قواعد التحقق أو حساب السعر أو الانتقال بين حالات الطلب في أكثر من موضع. استخرج الجزء المشترك إلى مكان واحد واضح.
- **KISS:** اختر أبسط تصميم يحقق المتطلب الحالي ويحافظ على سلامة البيانات.
- **YAGNI:** لا تنفذ تطبيق جوال أو تعدد عملات أو تكامل دفع أو تجريدًا مستقبليًا قبل وجود متطلب معتمد.
- أعد استخدام مكونات Blade، والسياسات، وقواعد التحقق، والـActions عند وجود منطق مشترك حقيقي.
- لا تنشئ `BaseController` أو `helpers` عامة أو Repository لكل Model تلقائيًا. أضف abstraction فقط عندما يزيل تكرارًا فعليًا أو يعزل حدًا خارجيًا.
- لا تجعل إعادة الاستخدام سببًا لصفوف عامة غامضة؛ يظل اسم الوحدة ومسؤوليتها مرتبطين بالمجال مثل الطلبات أو المنتجات.

### بنية Laravel عملية

نستخدم بنية Laravel المألوفة مع تجميع الملفات حسب المجال عند نموها. لا نُنشئ نظام Modules أو Domain framework إضافيًا في النسخة الأولى.

```text
app/
  Actions/
    Orders/
    Payments/
    Products/
  Enums/
  Filament/
    Resources/
    Pages/
    Widgets/
  Http/
    Controllers/
      Storefront/
      Customer/
      Seller/
    Middleware/
    Requests/
  Models/
  Notifications/
  Policies/
  Rules/
  View/
    Components/

resources/views/
  layouts/
  components/
  storefront/
  customer/
  seller/

routes/
  web.php

database/
  factories/
  migrations/
  seeders/

tests/
  Feature/
  Unit/
```

هذه خريطة إرشادية وليست أمرًا بإنشاء جميع المجلدات والصفوف مقدمًا. أنشئ الملف داخل المكان الموجود أو أضف مجلدًا عندما تظهر حاجة فعلية.

## 3. مسؤوليات الطبقات وتدفق الطلب

التدفق المعتاد:

```text
Route
  -> Middleware (مصادقة/صلاحيات عامة)
  -> Form Request (تحقق من المدخلات)
  -> Policy (صلاحية المستخدم على المورد)
  -> Controller
  -> Action عند وجود حالة استخدام متعددة الخطوات
  -> Model / Eloquent وTransaction عند الحاجة
  -> Event أو Notification بعد نجاح الحفظ
  -> Redirect أو View مع رسالة واضحة
```

- **Routes:** تربط URL بالعملية، وتطبق مجموعات المصادقة والـmiddleware. لا تضع فيها منطق أعمال.
- **Form Requests:** توحّد التحقق من المدخلات ورسائل الخطأ ذات الصلة. لا تعتمد على تحقق المتصفح وحده.
- **Controllers:** تنسق طلب HTTP، وتفوض التحقق والصلاحيات وقواعد العمل إلى المكونات المناسبة، ثم تعيد View أو Redirect.
- **Models:** تمثل بيانات المجال وعلاقات Eloquent وعمليات الحفظ الموجزة. تجنب جعل Model مستودعًا لكل منطق التطبيق.
- **Policies/Gates:** مصدر قرار الوصول إلى سجل أو عملية؛ إخفاء الزر في الواجهة ليس حماية.
- **Actions:** تستخدم لحالة استخدام واضحة ذات عدة خطوات أو قواعد، مثل إنشاء طلب وتقسيمه إلى طلبات بائعين وتثبيت الأسعار. لا تنشئ Action لكل عملية CRUD بسيطة.
- **Events/Notifications:** تستخدم للفصل بين نجاح العملية والتبليغ عنها. أرسل الإشعار بعد نجاح المعاملة، ولا تجعل فشل رسالة SMS يلغي إنشاء الطلب.
- **Filament:** يبقى منطق الصلاحية وقواعد العمل في Policies وActions ومكونات المجال، كي لا تتجاوز واجهة الإدارة قواعد النظام.
- **Blade:** للعرض والمكونات. استخدم escaping الافتراضي، ولا تحسب إجماليات مالية أو تقرر صلاحيات داخل القالب. تبقى عمليات التغيير خلف Routes وControllers مع CSRF والتحقق والصلاحيات.

## 4. قواعد تسمية وتنظيم الكود

- اكتب أسماء الكود بالإنجليزية، واضحة ومتسقة مع اصطلاحات Laravel: `Product`, `SellerProfile`, `OrderItem`.
- أسماء Models بصيغة المفرد، والجداول بصيغة الجمع وفق convention Laravel.
- استخدم أسماء طرق تصف الفعل، مثل `acceptOrder` أو `calculateDeliveryFee` عند وجود سبب لتلك الطريقة.
- ضع كل صفحة أو مورد أو سياسة في المجال الذي تملكه، ولا تنشئ نسخًا متوازية من المورد نفسه للبائع والإدارة بلا سبب.
- أبقِ ملفات اللغة والنصوص المعروضة للمستخدم في نظام الترجمة عند تفعيل الترجمة؛ لا تكرر النصوص الثابتة داخل عدة صفحات.
- اكتب تعليقات تشرح السبب أو قرارًا غير بديهي فقط، لا تعيد شرح الكود الواضح.
- لا تضع أسرارًا أو كلمات مرور أو مفاتيح API في الكود أو README أو Git. استخدم `.env`، وأضف أسماء الإعدادات فقط إلى `.env.example` دون قيم سرية.

## 5. قواعد المجال الخاصة بالمنصة

### المستخدمون والصلاحيات

- افصل بين هوية المستخدم وحساب المشروع في `User` و`SellerProfile`؛ لا تفترض أن لكل حساب مستخدم مشروعًا واحدًا إلى الأبد دون اعتماد القرار.
- افحص ملكية المنتج والطلب على الخادم في كل تحديث أو عرض خاص.
- لا تسمح للبائع بالوصول إلى طلبات أو منتجات بائع آخر بتغيير URL أو إرسال طلب HTTP يدوي.
- أي توثيق للبائع يجب أن يمر بحالة واضحة وقرار إداري محفوظ، ولا تعرض شارة موثوقية قبل الاعتماد.
- استخدم Laravel Policies أولًا. لا تضف حزمة أدوار وصلاحيات خارجية إلا إذا تطلبت الأدوار المركبة ذلك واعتمد الفريق الحزمة.

### المنتجات والمخزون

- احفظ الصور عبر Laravel Storage، وتحقق من نوع الملف وحجمه، ولا تثق باسم الملف القادم من المستخدم.
- استخدم معاملات قاعدة البيانات عند حجز المخزون أو تحديثه مع الطلب لتجنب البيع الزائد.
- سجّل تغييرات المخزون المهمة بسبب واضح، ولا تعدّل الرصيد عبر أكثر من مسار مستقل.
- اجعل المحافظة والتصنيف ووسم المنتج اليمني بيانات قابلة للإدارة، لا شروطًا ثابتة في الكود.

### الطلبات والمدفوعات والشحن

- استخدم Enum أو تمثيلًا مركزيًا واحدًا لحالات الطلب، وحدد التحولات المسموحة ومن يملك كل انتقال.
- خزّن لقطة اسم المنتج وسعره وخياراته ورسوم التوصيل وقت الشراء داخل عناصر الطلب؛ لا تعتمد على السعر الحالي للمنتج عند عرض فاتورة قديمة.
- استخدم DB transaction لإنشاء الطلب الرئيسي والطلبات الفرعية وعناصرها وحجز المخزون كوحدة متسقة.
- لا تستخدم `float` لحساب النقود. اعتمد نوع `DECIMAL` مضبوطًا أو عددًا صحيحًا بوحدة مالية موثقة، وطبّق تمثيلًا واحدًا عبر الأسعار والخصومات ورسوم التوصيل.
- لا تعتبر إثبات التحويل اليدوي دفعة مؤكدة قبل مراجعة مخولة. لا تخزن بيانات بطاقة دفع.
- اجعل طرق الدفع والمدن ومناطق التوصيل والرسوم إعدادات بيانات؛ لا تربط النظام بمزود يمني بعينه قبل التحقق من دعمه واعتماد قرار التكامل.
- سجّل من غيّر حالة الطلب أو الدفع ومتى، مع تجنب وضع بيانات حساسة في السجلات.

## 6. قاعدة البيانات والترحيلات

- كل تغيير مخطط قاعدة البيانات يمر عبر Migration قابلة للمراجعة، مع مفاتيح خارجية وفهارس وقيود مناسبة.
- أنشئ Factory وSeeder للبيانات التجريبية اللازمة للاختبارات والتطوير.
- لا تعدّل Migration سبق تشغيلها في بيئة مشتركة أو إنتاجية؛ أنشئ Migration جديدة للتعديل.
- لا تحذف عمودًا أو جدولًا أو بيانات قبل البحث عن جميع الاستخدامات، وتحديد خطة ترحيل/نسخ احتياطي وموافقة واضحة.
- استخدم Soft Deletes فقط عندما توجد حاجة أعمال للاحتفاظ بالسجلات، وحدد أثره على البحث والتقارير والعلاقات.
- لا تُدخل بيانات فعلية أو شخصية في Seeders أو Fixtures أو Git.
- الاختبارات تستخدم قاعدة بيانات اختبارية معزولة، ولا تستخدم قاعدة بيانات الإنتاج أو بيانات العملاء.

## 7. الأمان والخصوصية وإمكانية الوصول

- استخدم التحقق من المدخلات، CSRF وحماية Laravel الافتراضية، وescaping الافتراضي في Blade.
- لا تستخدم `$request->all()` مباشرة لتحديث Model؛ اختر الحقول المسموح بها بوضوح.
- طبق المصادقة والتفويض على كل مسار وكل عملية، واستخدم rate limiting للعمليات المعرضة للإساءة.
- افحص رفع الصور والملفات، وحدد أنواع الملفات وأحجامها ومكان تخزينها وصلاحية الوصول إليها.
- لا تعرض إثبات الدفع أو مستندات التوثيق في مسارات عامة.
- اجمع أقل قدر لازم من بيانات العملاء، ولا تسجل كلمات مرور أو رموز تحقق أو بيانات دفع في logs.
- صمم الواجهة RTL من البداية، واستخدم labels واضحة، وتباينًا مناسبًا، وحالات focus وتنبيهات أخطاء مفهومة.

## 8. الاختبارات والجودة

كل تغيير سلوكي جديد يجب أن يصاحبه اختبار يناسب أثره:

- **Unit:** لقواعد الحساب أو التحويل أو الانتقال بين الحالات عندما تكون مستقلة.
- **Feature:** لمسارات HTTP، المصادقة والصلاحيات، CRUD، إنشاء الطلب، الدفع، والتعامل مع المخزون.
- اختبر الحالات المرفوضة كذلك: بائع آخر، مستخدم غير مصادق، كمية غير متاحة، انتقال حالة غير مسموح، أو إثبات غير مراجع.
- استخدم Factories وبيانات صغيرة قابلة للفهم، ولا تعتمد على اتصال خارجي فعلي في الاختبارات.
- قبل الدمج شغّل اختبارات الجزء المعدل ثم مجموعة الاختبارات، وفحص التنسيق والأخطاء المتاحة.
- لا تُعطّل اختبارًا فاشلًا لإمرار التغيير؛ افهم سبب الفشل وعدّل السلوك أو الاختبار مع توثيق السبب.

أوامر متوقعة بعد إنشاء تطبيق Laravel وإعداد الاعتماديات:

```bash
php artisan test
vendor/bin/pint --test
npm run build
```

قد تختلف الأوامر حسب إصدارات Laravel وأدوات الاختبار التي يعتمدها المستودع. وثّق الأمر الفعلي في README بعد تأسيس المشروع.

## 9. إجراء إلزامي قبل أي إنشاء أو تعديل أو حذف

اتبع هذه الخطوات قبل لمس الملفات:

1. اقرأ هذا الدليل وREADME متطلبات المنتج، وحدد المتطلب وقبول التغيير المتوقع.
2. افحص الملفات والمسارات والاختبارات القريبة؛ ابحث عن تنفيذ قائم قبل إنشاء بديل.
3. افحص حالة Git والتغييرات الموجودة، ولا تستبدل أو تحذف تغييرات لم تنشئها أنت.
4. حدد مالك السلوك: Route، Controller، Policy، Action، Model، Blade، Filament، Migration أو Test.
5. حدد أصغر تعديل يحقق المتطلب، وما قد يتأثر من مستخدمين أو طلبات أو صلاحيات أو بيانات محفوظة.
6. قبل الإنشاء: تحقق أن الاسم والمسؤولية غير موجودين بالفعل، وأن الملف يقع في موضعه المتفق عليه.
7. قبل التعديل: حافظ على السلوك غير المرتبط بالطلب، وأضف/حدّث الاختبارات مع السلوك.
8. قبل الحذف: ابحث عن المراجع والمسارات والعلاقات والبيانات التابعة، وحدد أثر الحذف وخطة ترحيل أو أرشفة. لا تنفذ حذف بيانات أو Migration مدمرة دون موافقة صريحة ونسخة احتياطية مناسبة.
9. نفّذ التغيير بأقل مساحة ممكنة، ثم شغّل الاختبار الأضيق الذي يمكنه كشف الخطأ، وبعده فحوص المشروع ذات الصلة.
10. راجع `git diff` وتأكد أن التغيير لا يحتوي أسرارًا أو ملفات توليدية أو تعديلات غير مقصودة.
11. حدّث الوثائق إذا تغيرت طريقة تشغيل أو سلوك أو قرار معماري.

### بوابة مراجعة قبل اعتبار المهمة مكتملة

- هل يغطي التغيير متطلبًا واضحًا ويمكن وصفه باختبار؟
- هل أُعيد استخدام التنفيذ الحالي بدل تكراره؟
- هل بقيت قواعد العمل في مكان واحد؟
- هل تحققت الصلاحيات على الخادم؟
- هل تعالجت الأخطاء والحالات الحدية المهمة؟
- هل حُفظت البيانات القائمة ولم تُنفذ Migration مدمرة؟
- هل نجحت الاختبارات والفحوص ذات الصلة؟
- هل بقيت التغييرات محصورة في المطلوب؟

## 10. أسلوب العمل والتسليم

- قسم التطوير إلى مهام صغيرة: حسابات وصلاحيات، بائعون، تصنيفات ومنتجات، متجر عام، طلبات، ثم الدفع والتوصيل والتقارير.
- ابدأ كل ميزة بمسار رأسي صغير يعمل من الواجهة حتى قاعدة البيانات، ثم وسّعه بالاختبارات.
- لا تبدأ بالدفع الإلكتروني أو التسويق المتقدم قبل تثبيت تدفق الطلب المحلي وتشغيله يدويًا.
- في وصف الإنجاز، اذكر الملفات/السلوك الذي تغير، الفحوص التي شُغلت ونتيجتها، والقرارات أو القيود التي ما زالت مفتوحة.
- لا تنفذ Commit أو تغييرات بنيوية واسعة دون طلب أو اتفاق الفريق.
